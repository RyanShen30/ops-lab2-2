# O2 测前预测（运行 o2-net 之前写好，之后不改）

写于 2026-10-30，运行之前。

## 拓扑

- 主机 A（服务端，即任务 0～4 的实验主机）与主机 B（压测端）：均为华为云 `x1.4u.8g`（元数据 `metering.resourcespeccode`），4 vCPU、7556 MiB，同一可用区 cn-east-3c、同一 VPC、同一安全组，网卡均为 virtio_net。B 没有公网 IP。
- A 上的 enrolld 只监听 A 的内网地址的 18080 端口（8080 已被 lx 的服务占用于 127.0.0.1），绑 CPU 2-3；B 上直接运行 loadgen，请求 `GET /api/export?kb=256`，每个响应体 256 KiB。
- 华为云文档站有人机验证，未能查到 `x1.4u.8g` 的官方基准/最大带宽，所以只能按 L-07 第 19 页的方法给出换算关系，由实测找出上限。

## 带宽需求的换算

每个响应约 256 KiB = 262144 B，加上 HTTP 头和 TCP/IP 头（MTU 1500 时约 3%），在 A 的 eth0 上约 270 kB。

带宽需求 ≈ 到达率 × 262144 B × 8 × 1.03 ≈ **到达率 × 2.16 Mbit/s**。100 请求/秒约 0.22 Gbit/s，463 请求/秒约 1 Gbit/s，926 请求/秒约 2 Gbit/s，1852 请求/秒约 4 Gbit/s。

`sar -n DEV` 的 `txkB/s` 以 1024 B 为单位，预计约为 **到达率 × 264**（kB/s）。

## 预测

1. **上限之前**：A 的 eth0 `txkB/s` 随到达率线性增长，约为到达率 × 264；客户端延迟约为“一次往返 + 256 KiB 的发送时间”，几毫秒。
2. **先达到上限的是网络带宽，而不是 CPU。** 发送 256 KiB 主要是内核把数据拷进套接字缓冲区并分段（有 TSO），每个请求的 CPU 估计在 0.1～0.3 ms，两个核可以支撑数千请求/秒；B 上的 loadgen 只需读走数据，同样远未饱和。云主机的带宽上限按规格限速，预计在 1～8 Gbit/s 之间，对应约 **460～3700 请求/秒**；本次到达率从 50 逐级加到 3000 请求/秒（约 6.5 Gbit/s）。
3. **饱和时的征兆**：`txkB/s` 不再随到达率上升而形成平台，客户端吞吐停在平台，p99 迅速升高并出现 2 s 超时；同时 A 的 enrolld 所在核 CPU 仍低于 50%。云平台限速若以丢包实现，TCP 重传（`sar -n ETCP` 的 `retrans/s`、`nstat` 的 `TcpRetransSegs`）会在平台处明显增加；若以排队实现，则 `ss -tin` 中的 `rtt` 会变大、重传不多。预计会看到重传增加。
4. **按规格限速的云主机可能有突发能力**：阶段刚开始的几秒可能高于稳定平台，稳定值以阶段内后段的 `txkB/s` 为准。
